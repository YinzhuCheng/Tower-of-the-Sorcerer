# V3 c7 tight-bound bridge screening

## Goal

Before putting the discrete enemy-harvest + pure-HP access tightening into a proof-level suffix adapter, measure it across broad replay-verified c7 frontiers rather than only four representative bridges.

The screen samples three threshold-relevant c6 prefix families and expands each c7 goal frontier to 32 active goals. Every c7 certificate is authoritative-replayed before bound analysis.

## Per-bridge calculation

For each replay-verified c7 bridge:

```text
old admissible fixed-purchase UB
  -> exact reconstruction / cross-check
  -> indivisible 0/1 minimum-damage enemy Gold harvest
  -> strongest non-overlapping single pure-HP access constraint
  -> tight preview UB
```

The bridge is marked `prunable` when:

```text
tight preview UB <= V3 reference threshold 4459
```

The screen remains diagnostic-only and does not alter the actual Solver/pruning path.

## Metrics

Overall and per purchase stratum (p20/p21), report:

- bridge count;
- preview-prunable count;
- residual count;
- old UB range;
- tight UB range;
- tightening range;
- zero-damage Gold capacity;
- best future purchase count;
- fractional versus discrete harvest damage;
- pure-HP access lower bound and non-overlapping penalty.

## Promotion rule

If the screen eliminates a material fraction of the 32-goal c7 frontiers and all repository safety tests pass, the next implementation may promote the same formula into a **c7 bridge-level sound filter** in staged event-order analysis.

That first proof integration should still be boundary-only: compute the tightened bound once per replay-verified c7 bridge, discard only bridges with `tightUB <= threshold`, and leave every residual bridge on the existing suffix Solver. This avoids placing a relatively expensive 0/1 DP into the whole-game 50k hot path.

No bridge or candidate may be declared globally safe solely from this representative screen.
