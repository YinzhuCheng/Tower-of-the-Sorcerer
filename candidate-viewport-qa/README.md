# Candidate viewport evidence (CI-only)

Status: implementation and pure unit tests only. **No browser was launched locally and no screenshot has yet been generated by this package.** A completed remote Actions run and its actual artifact must be inspected before anyone claims screenshots are complete.

This directory is an isolated addition. It does not modify game sources, state/core, existing screenshots, the main CI workflow, or deployment settings. Apply it only to the selected candidate branch after publisher/root review. The A preset is for the newly frozen package on `candidate/a-tower-rewrite`, not an earlier A snapshot.

## Intended scope

- Real installed Google Chrome in GitHub-hosted Ubuntu, fresh disposable profile per viewport, standard sandbox and default GPU policy
- Desktop 1180 × 757 and narrow 390 × 844, DPR 1, actual viewport PNGs (not full-page downscaling)
- Normal game launch, an actual initial/current story dialogue, real visible UI skip/pause, real readiness, and exactly one keyboard move onto a plain adjacent floor cell
- A observes its content-scoped autosave via the app's logical storage API, 30-floor shape, real canvas, loading note and inert shell. The opening is intentionally allowed to precede canvas creation
- B/C use their own runtime identity and identity-scoped `campaign:…:auto` save; they never inherit A's 10-floor boot contract
- C3D reads its separate `c3d-prototype:campaign:…:auto` storage namespace and waits for actual WebGL2 rendering or the app's explicit 2D fallback notice. The C-M01 initial region uses the real 121-cell DOM grid with both canvases hidden, so its observed fallback is `DOM grid fallback`. Continuous-map regions instead report `Canvas2D fallback` only with a visible map canvas. It reports the renderer string, visible canvas dimensions, app render statistics, and Chrome GPU diagnostics
- No replay, fixtures, state setters, storage writes, artificial victory flags, CSS hiding, or browser-security weakening. Normal UI actions may cause the game itself to autosave

This is narrow-viewport and launch evidence. It is **not** a manual playthrough, a 30-floor proof, final-art approval, browser compatibility certification, phone-device testing, collision/occlusion acceptance, GPU performance measurement, or 3D quality approval. Width is emulated in desktop Chrome without mobile UA/touch simulation. Even a successful CI capture retains `threeDVisualAcceptance: false` and requires pixel inspection.

## Apply to one candidate

Copy the entire `candidate-viewport-qa/` directory into the exact candidate branch checkout. Copy only that candidate's reviewed workflow template into `.github/workflows/candidate-viewport-qa.yml` (remove `.example`). Do not put this workflow on main.

Build commands are explicit in `configs/*.json`. The runner adds no npm dependencies; C3D installs its existing locked Three.js dependency with lifecycle scripts disabled. A runs the normal build without silently disabling numeric validation. This smoke job supplements the existing candidate/root checks; it does not replace any full test/validation job.

Generate an equivalent workflow after an authorized config edit:

    node candidate-viewport-qa/workflow/make-workflow.mjs candidate-viewport-qa/configs/b.json .github/workflows/candidate-viewport-qa.yml

The workflow is limited to the exact candidate branch and permissions `contents: read`; checkout does not persist credentials. An initial push adding the workflow triggers it. `workflow_dispatch` on a branch-only new workflow may not be discoverable until GitHub registers it, so don't rely on dispatch for first execution. No secrets, third-party CI service, deploy tokens, account changes, or Vercel access are used.

## Local checks (no Chrome, no localhost)

    node --test candidate-viewport-qa/test/*.test.mjs

Only pure configuration/DOM contract tests run locally. The source-derived C3D initial-state fixture is used exclusively by unit tests; the browser runner never imports it. When the actual C3D package exists in the candidate checkout, one additional test cross-checks its live storage wrapper, initial identity/state/projection, compositor and initial canvas markup. In this isolated preparation directory that package may be absent, so that cross-check reports a skip. For a read-only cross-check against a verified existing C3D source tree, set `CANDIDATE_QA_C3D_SOURCE_URL` to its local `file:///…/prototypes/c-harbor-3d/` directory while running the same unit-test command. This performs no browser or server execution. `ci.mjs` and `capture()` explicitly reject use unless both `GITHUB_ACTIONS=true` and `CI=true`; **do not spoof these to bypass local execution restrictions.** The implementation is intended to run only in the separately authorized GitHub Actions environment.

## Artifacts and interpretation

Each successful viewport writes:

1. `01-startup.png` + JSON sidecar: initial real page, usually its opening dialogue
2. `02-current-dialog.png` + sidecar: the same actual current opening dialogue, deliberately captured before dismissal; this is not a fabricated later story state
3. `03-map-page-top.png` + sidecar: ready map page at document scroll top
4. `04-map.png` + sidecar: map after ordinary document scrolling, still exactly one viewport
5. `05-after-one-move.png` + sidecar: one actual adjacent move, same region, no victory
6. B additionally writes `06-resumed-dialog.png` + sidecar after resuming its paused story through the visible button

Thus the expected success artifact has 10 PNGs for A/C/C3D, 12 for B. Startup and current-dialog may look identical because they document the same real opening. Their JSON `kind` says so. Only B additionally exercises a later pause/resume path.

Per-viewport `report.json`, `render-status.json`, `browser-events.json`, and `chrome-stderr.log` record:

- requested and observed viewport, PNG dimensions, scroll offset, document overflow
- actual canvas pixel/CSS sizes and visibility; map/control rectangles
- real save identity/coordinates, render readiness and observed renderer
- console messages, JavaScript exceptions, HTTP status, resource 404s, failed requests, blocked external requests, unexpected native dialogs
- real mouse/keyboard inputs and before/after single-cell coordinates
- commit/branch/Chrome version/default GPU information and explicit evidence limitations

Root `.qa-artifacts/<id>/manifest.json` records exact config/build/branch/commit, build logs and both viewport outcomes. `server-requests.json` records the read-only local server's HTTP results. The server binds only `127.0.0.1`, serves only the built output with path/symlink containment, and is closed after the run. External page resource requests are blocked and recorded, so the test cannot silently use a Vercel preview/login or an outside asset in place of this build.

On readiness or browser failure, the runner attempts `failure.png` and `failure-observation.json`; the workflow uploads partial diagnostics with `if: always()`. A build failure has a build log/manifest rather than invented screenshots. A missing Chrome binary or sandbox failure stops with the actual diagnostic, without retrying with unsafe flags.

`captured` means that required captures and DOM/move checks completed. `captured-with-warnings` can include horizontal overflow, browser warnings, or actual 2D fallback. Neither is a visual design pass. Resource/JS errors fail the job; a missing automatic `favicon.ico` is recorded as a non-blocking warning. Unavailable WebGL2 is a truthful fallback result, never a 3D approval. Read the pixels and render report before accepting narrow layout or artwork.

## Deliberate exclusions

The current config rejects arbitrary page JavaScript, remote URLs, custom Chrome flags and fixture inputs. It does not expose certificate replay. If that is added later, it needs explicit `certificate-driven QA` labeling and a separate reviewed UI action contract; it still cannot be described as manual completion.

No test here reads arbitrary local data, changes OS security settings, disables sandboxing, disables web security, hides errors/scrollbars, or forces software GPU rendering. There is no workaround for a restricted local browser.
